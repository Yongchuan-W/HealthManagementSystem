## 摘要

健康管理系统是一个面向普通家庭的一站式健康记录与 AI 健康助理平台。系统把饮食、运动、睡眠、体征、体重、情绪、女性生理周期、家人健康档案与体检报告这些原本分散在纸笔、备忘录和各类 App 中的数据，收敛到同一份个人健康档案中，并让大模型基于这份真实数据给出可执行建议。

技术上有三个特点：

1. **零依赖部署**：后端只用 Python 标准库实现 HTTP 服务、路由、鉴权与 SQLite 持久化，不需要 Flask/Django、不需要 Node 构建，一台 1 核 1G 的云主机即可运行，`python web.py` 一条命令启动。
2. **AI 不是外挂而是数据入口**：AI 健康小管家不仅能对话，还能把用户一句话（如「午饭吃了番茄炒蛋和米饭」）直接写成结构化的饮食记录，把体重、运动、睡眠写入对应模块；图片识别则把餐食照片和体检报告转成结构化指标，回填到体征卡与营养目标。
3. **数据可信优先，界面克制**：系统对「未记录」与「已记录但异常」做了严格区分，没有采集到的体征一律显示「—」，评分在无数据时同样显示「—」，绝不用默认值制造"一切正常"的错觉；视觉上采用浅苔绿医疗配色，卡片按主次分两档底色，装饰元素全部走 CSS/SVG 背景层，不占用布局。

## 1 项目概述

### 1.1 背景

家庭健康管理存在三个断点：

- **记录断点**：体重、血压、血糖分散在不同设备或纸本；饮食与运动靠回忆，难以连续。
- **理解断点**：拿到体检报告后，普通人看不懂 BMI、体脂率、血糖之间的关联，更不知道下一步该吃什么、动多少。
- **执行断点**：通用健康建议（"少油少盐""每周运动 150 分钟"）缺乏与个人数据的连接，看完即忘。

大模型具备理解自然语言与图片的能力，但通用聊天机器人不知道用户昨天吃了什么、体重多少、目标是什么，给出的建议往往空泛甚至矛盾。把「个人健康数据」与「大模型」打通，是解决上述断点的关键。

### 1.2 目标

- 用最低的操作成本完成日常健康记录（一句话、一张照片即可）；
- 把体检报告翻译成普通人能执行的动作：先看风险，再吃对、动对；
- 让每一条建议都能追溯到用户自己的数据与公开指南；
- 在一个可离线、可私有部署的架构内完成，降低使用门槛与隐私风险；
- 兼顾家庭场景：老人、慢病人群的血压、用药、复诊提醒可以在同一系统内管理。

### 1.3 主要成果

| 维度 | 成果 |
| --- | --- |
| 功能 | 6 大模块、23 张数据表、40 余个 REST 接口，覆盖饮食/运动/睡眠/体征/情绪/女性健康/家人健康/体检报告/AI 助理；登录后默认进入 AI 体检解读首屏 |
| AI | 体检报告 OCR、对话式记录、餐食图片识别、语音输入、个性化建议生成 |
| 工程 | 单文件服务端 + 单页前端，零第三方运行依赖；Docker 之外的最简部署形态 |
| 质量 | 完成一轮黑盒体验走查与安全走查，18 项缺陷全部整改并回归 |
| 上线 | 已通过 Cloudflare 隧道部署在公网 HTTPS 域名，支持手机与桌面浏览器 |

## 2 需求分析

### 2.1 用户画像与场景

| 用户 | 核心诉求 | 典型场景 |
| --- | --- | --- |
| 都市白领（25–35 岁） | 控制体重、改善作息 | 上传体检报告，先拿到风险提示与今日食谱，再照着记录 |
| 体检报告"看不懂"人群 | 知道异常项，但不知道下一步吃什么、动多少 | 拖拽报告截图，30 秒拿到风险、食谱、运动三张行动卡片 |
| 健身人群 | 记录训练量、观察体重趋势 | 点击日期补记当天运动，查看近 7 天完成度 |
| 慢病 / 中老年 | 血压血糖连续记录、按时用药 | 家人代录血压，设置复诊与吃药提醒 |
| 女性用户 | 经期与易孕期预测 | 记录经期开始日，自动推算排卵日与下次经期 |
| 家庭照护者 | 统一管理多位家人 | 在一个页面查看父母的血压、用药与提醒 |

### 2.2 功能需求

1. **健康数据总览（登录后默认首屏）**：核心体征、三项评分、异常提醒与体检报告分析集中在首屏；没有引导表单拦截，资料可在需要时从「修改基本信息」补充。
2. **健康数据总览**：核心体征卡（体重、BMI、体脂率、血压、血糖）、三条评分（综合/饮食/运动）、异常提醒、体检报告分析。
3. **饮食**：按餐次记录、食物库检索、热量与三大营养素统计、目标对比、AI 餐食识别、综合饮食建议。
4. **运动**：运动类型选择、时长与强度记录、近 7 天柱状图、按日期补记、运动计划。
5. **睡眠**：入睡/起床时间与时长、近 7 天柱状图、睡眠质量提示。
6. **家人健康**：多成员档案、血压/用药/复诊记录、关怀提醒。
7. **科普资讯**：RSS 聚合 + 站内封面、关键词筛选、速读摘要。
8. **AI 健康小管家**：悬浮对话窗，支持健康问答、数据写入、页面跳转、图片与语音输入。
9. **账号体系**：注册/登录/注销、找回密码（邮箱验证码）、修改密码、个人档案、数据云同步。

### 2.3 非功能需求

- **性能**：首屏可交互 < 2 s（同城网络），接口 P95 < 500 ms（AI 接口除外）；
- **可用性**：AI 服务不可用时，所有非 AI 功能必须继续可用，并给出可读的降级提示；
- **安全**：密码不可逆存储、会话不可被 JS 读取、接口按用户隔离、上传文件不暴露真实路径；
- **隐私**：健康数据默认留在自建服务器，不接入第三方广告或分析 SDK；
- **兼容**：桌面与移动端自适应，主流 Chromium / Safari / 微信内置浏览器可用。

## 3 系统架构

### 3.1 总体架构

```text
┌──────────────────────────────────────────────────────┐
│  浏览器（桌面 / 手机）                                │
│  单页应用：HTML + CSS + 原生 JS，SVG 雪碧图           │
│  ├─ 页面模块：健康数据 / 饮食 / 运动 / 家人 / 睡眠 ...  │
│  ├─ 状态层：内存状态 + localStorage 缓存 + 云端同步   │
│  └─ AI 入口：报告上传首屏、悬浮对话窗、餐食与体检图片  │
└───────────────────────────┬──────────────────────────┘
                            │ HTTPS（Cloudflare 终止 TLS）
┌───────────────────────────┴──────────────────────────┐
│  应用服务：Python 标准库 ThreadingHTTPServer          │
│  ├─ app.py      请求解析、静态资源、ETag/304、错误处理 │
│  ├─ routes.py   路由表 + 40 余个业务接口 + 报告解读编排 │
│  ├─ auth.py     PBKDF2 口令、会话、Cookie、白名单      │
│  ├─ db.py       SQLite 连接、建表、迁移、备份          │
│  ├─ ai.py       OpenAI 兼容客户端（对话/视觉/JSON）    │
│  ├─ asr.py      语音识别（可选）                       │
│  ├─ mailer.py   SMTP 邮件（找回密码）                  │
│  └─ telemetry.py 请求量、错误率、模型耗时采样          │
└──────────┬───────────────────────┬───────────────────┘
           │                       │
     health.db（SQLite WAL）   外部模型服务（OpenAI 兼容）
```

### 3.2 前端设计

- **单文件交付**：样式、脚本、图标全部内联在 `PAGE_HTML` 中，服务端直接返回，省去静态资源服务器与构建链，首屏只有一个 HTML 请求。
- **视觉体系**：以浅苔绿为主调（主色 `#455C3D`、卡片 `#E2EADA`、主卡 `#D8E2CD`、背景 `#F4F7F1`），医疗青 `#0E7C74`、暖沙 `#B08A5A`、浅紫 `#6E5FA8` 作局部辅助色，用于评分卡、餐次标签、关怀提醒与 AI 对话窗，避免整页单一绿色；饮食近七日热量柱状图用雾蓝（`#A6C8DE → #3F6D91`）与绿色卡片形成冷暖对比，无记录日改为浅蓝空态。核心体征卡在右上、右下用极淡的同色光晕叠加散点与心电波形，全部为 CSS/SVG 背景层，不新增节点、不影响布局。
- **可读性优先**：卡片分「主卡 / 次卡 / 卡内白色数据块」三档底色建立层级；异常与警示保留暖色语义，装饰透明度控制在 10%–30%，保证文字对比度。
- **路由**：`switchPage(name)` 控制 `.page.active`，配合 `hidden` 属性做双层保护，避免权限页面误显示。
- **状态**：内存对象 + `localStorage` 缓存（按账号命名空间），登录后与服务端 `/api/sync` 双向同步；离线可继续记录，恢复网络后合并。
- **图表**：手写 SVG/CSS 柱状图与折线图，无第三方图表库；统一「近 7 天、今天在最后一格」的时间窗，避免各模块口径不一。
- **性能**：`loading="lazy"` 封面图、图片上传前 Canvas 压缩（长边 ≤ 1280）、首屏延后初始化非关键模块。

### 3.3 后端设计

- **路由**：装饰器注册 `(method, pattern, auth_required, handler)`，路径参数用 `<id>` 占位；统一 `ApiError` 转 JSON。
- **请求上下文**：`Context` 封装用户、token、body、query、headers，业务函数只关心参数与返回值。
- **数据隔离**：所有业务表带 `user_id`，SQL 全部参数化，禁止字符串拼接。
- **并发**：`ThreadingHTTPServer` + SQLite WAL，读多写少场景下吞吐足够；写操作保证短事务。
- **可观测**：`telemetry` 采样请求路径、状态码、耗时与模型调用，管理员可在数据大屏查看。

### 3.4 数据模型（主要表）

| weight_records / vital_records | 体重历史、体征记录（体脂、BMI、血压、血糖） |
| meal_records / sport_records / sport_goals | 饮食、运动、运动目标 |

## 4 AI 技术方案

### 4.1 模型选型与接入方式

- **协议**：采用 OpenAI 兼容的 `/v1/chat/completions`，通过 `HM_AI_API_BASE` + `HM_AI_MODEL` 两个环境变量即可切换供应商（DeepSeek / 豆包方舟 / 通义 / 自建 vLLM）。
- **默认配置**：`https://api.deepseek.com/v1` + `deepseek-flash`；纯文本对话超时 20 s，视觉请求单独放宽至 60 s。
- **鉴权**：API Key 只存服务器环境变量，前端永远拿不到；仓库提供 `.env.example`，真实 Key 不入库。
- **降级**：未配置 Key 或模型返回错误时，接口返回可读提示（如「AI 服务暂不可用，请稍后重试」），页面其他功能不受影响；AI 不可用时用户仍可手动录入。

### 4.2 对话式记录：从自然语言到结构化数据

AI 小管家不是"只会聊天"的窗口，而是一条数据入口：

1. 前端把用户消息与**当前页面上下文**一起提交到 `/api/ai/chat`；
2. 服务端拼装系统提示词：角色设定 + 输出规范 + 当前用户健康摘要（体重、目标、近 7 天饮食运动、体征）+ 页面功能索引；
3. 模型返回自然语言答复，同时给出结构化动作（如 `{"action":"add_meal","payload":{...}}`）；
4. 服务端校验动作的参数范围（热量、克数、时长上限），通过后写入对应表；
5. 前端就地刷新卡片，并提示「已记录：番茄炒蛋 约 180 kcal」。

这种"自然语言 → 受控动作"的做法，比让模型直接生成自由文本再解析更可靠：动作白名单、参数校验、失败回退三者结合，把大模型的不确定性限制在可控范围内。

### 4.3 图片识别：餐食与体检报告

**餐食识别**

- 上传前在浏览器用 Canvas 压缩（长边 ≤ 1280、JPEG 质量 0.82），单张通常 < 200 KB，显著降低上传与推理耗时；
- 服务端以 `data:image/jpeg;base64` 传入多模态模型，`temperature=0.1`，要求返回严格 JSON：菜品列表、每项估算克数、热量、蛋白质/碳水/脂肪；
- 解析时做三层兜底：直接 `json.loads` → 截取首个 `{...}` → 正则提取数字；失败自动重试一次；
- 识别结果回填到当前餐次，用户可修改克数后保存；识别期间按钮禁用并显示「识别中…」，避免重复提交。

**体检报告识别**

- 同一视觉接口，提示词改为"抽取指标"：日期、体重、体脂率、BMI、血压、血糖、总胆固醇等；
- 只回填识别到的字段，未识别的保持「—」，不猜测、不补全；
- 识别结果回填到体征卡与体检报告区，作为后续查看与记录的依据；
- 报告区在无数据时整块隐藏，避免示例数据被误认为真实体检结果。

### 4.4 上下文增强（RAG-lite）

考虑到部署成本与响应时延，本项目没有引入向量数据库，而是采用"轻量检索 + 上下文注入"的折中方案：

1. **本地知识**：内置常见食物营养表、运动 MET 值表、页面功能索引（哪个页面能做什么、按钮在哪）；
2. **个人数据**：把近 7 天饮食/运动/睡眠聚合、最新体征、目标体重与热量目标压缩成一段 300 字以内的摘要；
3. **按需注入**：根据用户问题关键词（吃/练/睡/血压/经期）选择相关片段拼进系统提示词，而不是把全部数据塞进去，既控制 token 成本，也减少模型被无关信息干扰。

这套方案在保持低延迟的同时，让回答能引用具体数字（「你近 7 天平均睡眠 6.4 小时」），明显优于无上下文的通用回答。后续可平滑替换为向量检索：只需把"选择片段"的函数换成 embedding 召回。

### 4.5 稳定性与成本控制

| 问题 | 措施 |
| --- | --- |
| 模型偶发超时 | 文本 20 s / 视觉 60 s 分级超时 + 一次自动重试 |
| 返回非 JSON | 三级解析兜底 + 参数校验 + 失败提示手动录入 |
| 图片过大 | 前端压缩 + 服务端大小限制 |
| 调用成本 | 控制 max_tokens（文本 1200、视觉 2000）、上下文摘要限长、按用户日配额限流 |
| 接口被刷 | 注册按 IP 限流（5 次/10 分钟），AI 接口按账号配额 |

### 4.6 AI 安全与合规

- 提示词中明确"不提供诊断、不替代医生"，涉及用药与急症时引导就医；
- 健康建议必须给出数据依据，禁止编造用户未记录的指标；
- 用户可随时删除账号，业务数据随外键级联清除；
- 模型供应商可切换，便于在隐私要求高的场景改为私有化部署。

## 5 核心功能实现

### 5.1 健康数据总览（首屏）

- **核心体征卡**：体重、BMI、体脂率、血压、血糖五项，未记录显示「—」，记录后按中国成人标准着色（正常/偏高/偏低）；卡片右上、右下有极淡的同色光晕、散点与心电波形装饰。
- **评分体系**：综合 = 饮食 40% + 运动 40% + BMI 20%。无任何饮食与运动记录时，三张评分卡分别用三档浅苔绿显示「—」而不是 0 分，并在提示条说明公式与入口。
- **异常提醒**：只对已记录的指标判断，未记录的指标不参与"是否正常"的结论。
- **体检报告**：识别后展示日期、指标与综合分析，报告区在无数据时整块隐藏。

### 5.2 饮食

- 早/午/晚/加餐四个餐次，支持食物库搜索、份量选择、自定义食物；
- 实时统计热量与三大营养素，与个人目标对比（目标由体重、身高、年龄、性别、活动量按 Mifflin-St Jeor 计算）；
- 无体重或身高时目标显示「—」，并提示先去记录，不用默认身高编造目标；
- 综合饮食建议基于近 7 天真实记录生成，记录不足时明确提示"再记录 2–3 天"。

### 5.3 运动

- 运动类型（跑步、快走、骑行、游泳、力量训练等）+ 时长 + 强度，自动估算消耗；
- 近 7 天柱状图，点击任意日期可补记当天运动；
- 与饮食评分联动：周运动量达标后运动评分提升。

### 5.4 睡眠与情绪

- 记录入睡/起床时间，自动计算时长，分钟支持 0–59 任意值；
- 近 7 天柱状图，未记录日期留空而不是显示「—」；
- 情绪时间轴记录每日心情，同样采用近 7 天窗口。

### 5.5 女性健康

- 记录经期开始日、经期长度、周期长度，推算排卵日、易孕期、下次经期；
- 未记录时全部显示「—」；保存的旧记录超过两个周期不再参与预测，避免展示已经过去的日期。

### 5.6 家人健康

- 多成员档案（称呼、年龄、关系、手机号）；
- 每位成员可记录血压、用药、复诊，并设置关怀提醒；
- 空状态给出「添加家人」引导，不预置任何示例成员。

### 5.7 科普资讯

- 服务端聚合公开健康 RSS 源，清洗标题与摘要，失败自动切换备用源；
- 站内封面图 + 渐变兜底，图片懒加载，加载失败静默移除；
- 支持关键词筛选、速读摘要、来源标注与原文跳转。

### 5.8 AI 健康小管家

- 右下悬浮球，桌面与移动端均可唤起；打开弹窗时自动隐藏悬浮球避免遮挡；
- 支持文本、语音（可选 ASR）、图片三种输入；
- 能回答健康问题、解释评分、跳转页面、写入饮食/运动/体重/睡眠记录；
- 会话持久化，换设备后仍可继续。

## 7 安全与可靠性

| 风险 | 措施 |
| --- | --- |
| 口令泄露 | PBKDF2-HMAC-SHA256，20 万次迭代 + 16 字节随机盐，`hmac.compare_digest` 校验 |
| 会话劫持 | 随机 32 字节 token，30 天有效；HttpOnly + SameSite=Lax Cookie；HTTPS 下自动加 `Secure` |
| XSS | 前端统一转义用户输入，避免 `innerHTML` 直接拼接未过滤内容 |
| SQL 注入 | 全部参数化查询 |
| 越权访问 | 所有业务接口校验登录态并按 `user_id` 过滤；管理员接口额外校验角色 |
| 枚举与爆破 | 注册按 IP 限流；登录失败统一提示；找回密码验证码 10 分钟有效、5 次上限 |
| 上传风险 | 限制类型与大小，文件名随机化，仅通过受控路由读取 |
| 密钥泄露 | Key 只存环境变量；`.env` 与 `ai_local.env` 已加入 `.gitignore` |
| 数据丢失 | SQLite 每日备份到 `backups/`，保留最近 N 份 |

## 9 创新点

1. **AI 作为数据入口，而非聊天装饰**：把"说一句"变成结构化记录，降低健康类 App 最常见的"记录成本高 → 坚持不了"的流失。
2. **一张体检单打通记录与建议**：识别结果直接回填体征，报告、评分、饮食运动建议共用同一份数据，不做互不相干的功能堆叠。
3. **克制而统一的视觉体系**：浅苔绿主调配两档卡片底色，医疗青、暖沙、浅紫只做局部点缀，热量柱状图用雾蓝拉开冷暖对比；心电、散点等医疗符号只做 10%–30% 透明度的背景层，既有辨识度又不干扰读数。
4. **受控动作 + 参数校验的动作层**：在提示词之外加白名单与范围校验，兼顾自然语言灵活性与数据可靠性。
5. **RAG-lite 的性价比取舍**：不引入向量库，用本地知识 + 数据摘要 + 关键词路由实现"有依据的回答"，部署成本与延迟都更低，且可平滑升级为向量检索。
6. **可信空状态设计**：未记录 ≠ 正常，未记录 ≠ 0 分，未识别字段保持「—」，从产品层面杜绝"编造健康数据"。
7. **极简部署形态**：零运行依赖 + 单文件前端，适合家庭 NAS、树莓派、低配云主机，也便于课程/竞赛评审复现。
8. **家庭维度**：把"个人健康"扩展为"家庭健康"，符合中国家庭代际照护的真实场景。

## 10 社会价值与商业潜力

**社会价值**

- 降低健康记录门槛：老人可由子女代录并收到提醒，慢病人群能连续观察血压血糖趋势；
- 提升健康素养：每条建议都带数据依据，帮助用户理解"为什么"；
- 隐私友好：支持私有部署，健康数据不必交给第三方平台。

**商业潜力**

- **To C 订阅**：高级 AI 建议、家庭多成员、体检报告解读；
- **To B 合作**：社区养老、体检机构、企业健康福利，可按机构私有化部署；
- **硬件联动**：接入血压计、体脂秤、手环数据，形成"设备 → 记录 → 建议"闭环；
- **成本可控**：以当前模型价格测算，单用户日均 3 次识别的成本在几分钱量级，具备规模化条件。

## 13 不足与展望

1. **视觉识别准确率**受模型能力限制，复杂摆盘、低清晰度报告仍需人工修正；后续可接入专用 OCR 或更大参数模型，并以用户修正结果做反馈优化。
2. **RAG 仍是轻量版**，尚未引入向量检索与医学知识库；后续可在保持低延迟的前提下增加分层检索，让饮食/运动建议引用更细的指南条目。
3. **识别与建议依赖模型与网络**，网络受限时只能手动录入；异常指标仍需引导用户就医复查。
4. **无原生 App**，离线能力依赖浏览器缓存；可考虑 PWA 或小程序形态。
5. **提醒通道单一**，目前以站内提醒为主，可扩展短信、微信服务号。
6. **缺少临床验证**，所有建议均为健康管理范畴，不构成医疗诊断。
